# admin-dashboard（代号 houtai）— 研发流程总览

> 本文档模拟一家互联网公司从立项到上线的标准研发流程，说明每个阶段的**角色、输入、输出（交付物）、评审门禁（Gate）与完成标准**。所有阶段文档位于本目录，接口与字段一律以 [`../开发文档.md`](../开发文档.md) 为准。

## 一、项目基本信息

| 项 | 内容 |
| --- | --- |
| 项目名称 | 后台管理 + 数据看板（仓库 `admin-dashboard`，代号 houtai） |
| 项目目标 | 把「登录鉴权 → 布局与菜单 → 用户/角色管理 → 数据看板」串成一个完整可部署的前后端分离项目 |
| 技术栈 | 前端 **React 19.3 + Vite 8.3（脚手架已生成）** + React Router v6 + antd 5 + Zustand + ECharts 5 + axios；后端 **Node.js + Express 4 + MySQL 8**；鉴权 **JWT(HS256) + bcrypt** |
| 代码仓库结构 | `backend/`（后端 Express，端口 **3000**，前缀 `/api`）<br>`mock/`（零依赖 Mock，端口 3001）<br>`frontend/`（Vite 脚手架，端口 5173，业务页面待写）<br>`UI设计稿/`、`研发流程/` |
| 运行方式 | 后端 `cd backend && npm run dev`；前端 `cd frontend && npm run dev`（proxy 指向 3000） |
| 默认访问 | 后端 `http://localhost:3000/api`；前端 `http://localhost:5173`；Mock `http://localhost:3001/api` |
| 演示账号 | `admin / 123456`（超级管理员）、`operator / 123456`（运营） |

## 二、组织与角色（RACI）

| 角色 | 代号 | 核心职责 | 关键交付物 |
| --- | --- | --- | --- |
| 项目经理 | PM | 排期、资源、风险、验收组织 | 项目计划、里程碑、周报 |
| 产品经理 | PO | 需求定义、优先级、验收标准 | PRD、需求变更单 |
| UI/UX 设计师 | UI | 视觉与交互设计、设计规范 | 设计稿、设计规范、切图 |
| 前端开发 | FE | 页面/交互/联调 | 前端代码、自测记录 |
| 后端开发 | BE | 接口/数据库/服务 | 后端代码、接口文档、SQL |
| 测试工程师 | QA | 用例、执行、缺陷跟踪 | 测试计划、用例、测试报告 |
| 运维 | OPS | 环境、发布、监控、回滚 | 发布方案、上线记录 |

> 小团队可一人多角色，但**评审门禁不可省**：每个 Gate 至少有一次"非作者本人"的评审。

## 三、研发流程六阶段与门禁

```
S1立项 →[G1立项评审]→ S2需求 →[G2需求评审]→ S3设计+技术 →[G3设计/技术评审]
→ S4开发联调 →[G4提测评审]→ S5测试 →[G5发布评审]→ S6上线 → 复盘
```

| 阶段 | 名称 | 主要活动 | 输出交付物 | 门禁（Gate）通过标准 |
| --- | --- | --- | --- | --- |
| S1 | 项目立项 | 明确目标、范围、里程碑、资源 | 《项目计划》《里程碑》 | G1：范围与排期达成共识 |
| S2 | 需求分析 | 需求调研、原型、编写 PRD | 《需求文档 PRD》 | G2：需求评审通过、验收标准明确、优先级确定 |
| S3 | 设计 + 技术方案 | UI 设计、技术方案、接口约定、DB 设计 | 《UI 设计规范》《技术方案与接口契约》 | G3：设计稿定稿、接口契约对齐真实后端、技术风险有对策 |
| S4 | 开发 + 联调 | 前后端开发、接口联调、自测 | 《开发协作规范》、代码、自测单 | G4：功能自测通过、无 P0/P1 阻塞缺陷、可提测 |
| S5 | 测试 | 用例执行、缺陷修复、回归 | 《测试计划与用例》《测试报告》 | G5：用例通过率达标、P0/P1 缺陷清零、回归通过 |
| S6 | 发布上线 | 部署、验证、监控 | 《上线发布与回滚》、上线记录 | 上线验证通过、可回滚 |

## 七、变更与缺陷管理

**需求变更**：任何范围/验收标准变化 → 提交《需求变更单》→ PO 评估 → PM 更新排期 → 评审确认。禁止口头改需求。

**缺陷生命周期**：

```
新建(New) → 指派(Assigned) → 修复中(Fixing) → 待验证(Resolved)
→ 验证通过(Verified)→ 关闭(Closed)   /  验证不通过 → 重新打开(Reopened)
```

**缺陷严重等级**

| 等级 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 致命 | 崩溃/数据丢失/核心流程不可用 | 立即修复，阻塞发布 |
| P1 严重 | 主功能异常、明显错误 | 发布前必须修复 |
| P2 一般 | 次要功能/体验问题 | 可排期修复 |
| P3 轻微 | 文案/样式细节 | 可延后 |
