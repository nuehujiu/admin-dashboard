## 1. Git 分支模型（Git Flow）

```
main         ●──────────────●──────────●   (仅存放可发布版本)
              \            /            /
release        ●──●──●    ●──●──●      (发布分支，修发布期缺陷)
              /          /
develop  ●───●──●───●───●───●───●      (集成分支，日常合并)
          \  /    \  /
feature/*  ●●      ●●                   (功能分支，一个需求一分支)
hotfix/*                     ●──●       (线上紧急修复，直接基于 main)
```

| 分支 | 用途 | 命名 | 起点 | 合并去向 | 合并方式 |
| --- | --- | --- | --- | --- | --- |
| `main` | 生产可用版本，受保护 | — | — | — | 只接受 PR |
| `develop` | 日常集成，受保护 | — | `main`（首次） | — | 只接受 PR |
| `feature/*` | 新功能 | `feature/goods-export`、`feature/role-menu-tree` | `develop` | `develop` | **Squash** |
| `release/*` | 发布准备 | `release/v1.0.0` | `develop` | `main` → 再回灌 `develop` | **Merge --no-ff** |
| `hotfix/*` | 线上热修 | `hotfix/login-500` | `main` 的 Tag | `main` → 再回灌 `develop` | **Merge --no-ff** |

**规则**：功能开发从 `develop` 拉出，完成后合并回 `develop` 需走 PR；发布从 `develop` 出 `release`，验证后合 `main` 并打 Tag。

### 1.1 GitHub 上的落地配置（单人项目也照做）

在仓库 **Settings → Branches** 给 `main` 和 `develop` 各加一条保护规则（Public 仓库免费）：

| 设置项 | 值 | 原因 |
| --- | --- | --- |
| Branch name pattern | `main`；`develop` | 两条长期分支都要锁 |
| Require a pull request before merging | ✅ | 这是「不能直接 push 主干」的唯一开关 |
| Required approvals | **0** | 单人项目没有第二个人能批，见 §1.2 |
| Require status checks to pass | ✅（选 `CI / check`） | 用机器替代人工 Review 的第一道闸 |
| Do not allow bypassing | ✅ | 连自己也不能绕过 |
| Allow force pushes / Allow deletions | ❌ | 主干历史不可重写 |

**关键一条**：不要勾 **Require linear history** —— Git Flow 里 `release → main`、`hotfix → main`、`main → develop` 回灌都是 merge commit，开了线性历史会被直接拒掉。

**Settings → General → Merge button**：勾 `Allow merge commits` + `Allow squash merging`，**关掉 `Allow rebase merging`**（rebase 会重写 release 上的提交 SHA，回灌 develop 时对不上）。

### 1.2 单人项目的 Review 替代（§4 第 10 条的例外）

本仓库唯一前端 = 无第二人可 Review。用下面三条替代「非作者 Review」，任一缺失不得合并：

1. **自审 PR diff**：自己在 Files changed 逐行走一遍，重点看有没有误提交 `.env`、`console.log`、`node_modules`；
2. **CI 必须绿**（`.github/workflows/ci.yml`：语法检查 + OpenAPI JSON 校验）；
3. **PR 描述里贴自测结论**（勾 §7 清单中受影响项），不信口头「测过了」。

### 1.3 合并策略矩阵（照着点，别随手用默认按钮）

| 场景 | GitHub 按钮 | 本地等价命令 | 理由 |
| --- | --- | --- | --- |
| `feature/* → develop` | **Squash and merge** | `git merge --squash` | develop 保持「一功能一提交」，历史可读 |
| `release/* → main` | **Create a merge commit** | `git merge --no-ff` | 保留发布批次，回灌 develop 与 revert 都靠它 |
| `hotfix/* → main` | **Create a merge commit** | `git merge --no-ff` | 同上 |
| `main → develop`（回灌） | **Create a merge commit** | `git merge --no-ff origin/main` | 让两条长期分支 SHA 对齐，避免重复提交 |

> 反例：`release → main` 用 Squash，会把 release 上的一串提交压成 1 个新 SHA；之后再 `main → develop` 回灌，develop 上那批原提交还在，git 会把它们当成「另一条历史」，后续每次合并都重复冲突。

### 1.4 一次完整的版本发布（单人执行时序）

> 命令在 PowerShell 7（本机 7.6.4）下可直接粘贴；若用 Windows PowerShell 5.1，把 `&&` 拆成两行分别执行。

```powershell
# ① 发布分支从 develop 出
git switch develop && git pull --ff-only origin develop
git switch -c release/v1.0.0
# 只允许 fix/docs/test：修发布期缺陷，不加新功能
git commit -am "fix(settings): release 前修复主题色校验文案"
git push -u origin release/v1.0.0
# ② 网页开 PR：release/v1.0.0 → main，选 Create a merge commit
# ③ 合并后打 Tag（只打在 main 上）
git switch main && git pull --ff-only origin main
git tag -a v1.0.0 -m "发布 v1.0.0：30 接口 / 8 表 / 13 菜单"
git push origin v1.0.0
# ④ 回灌 develop（关键，少了这步下个版本会重复提交）
git switch develop && git pull --ff-only origin develop
git merge --no-ff origin/main -m "chore(release): 回灌 v1.0.0 到 develop"
git push origin develop
# ⑤ 删发布分支 + 网页创建 Release（附 v1.0.0 tag，写变更摘要）
git push origin --delete release/v1.0.0
git branch -d release/v1.0.0
```

### 1.5 线上热修（`hotfix` 必须基于 Tag，不是基于 main 的最新提交）

```powershell
git fetch --tags origin
git switch -c hotfix/login-500 v1.0.0     # 从发布点拉，不带未发布内容
git commit -am "fix(auth): 修复 token 过期后未跳登录页"
git push -u origin hotfix/login-500
# PR: hotfix/login-500 → main，Create a merge commit
# 合完：tag v1.0.1 → push tag → 回灌 develop → 删分支（同 §1.4 ③④⑤）
```

**Tag 规范**：`vMAJOR.MINOR.PATCH`；`release` 递增 MINOR，`hotfix` 递增 PATCH。

### 1.6 日常提交的自动化边界（`scripts/daily.ps1`）

唯一前端每天提交代码用这个脚本，**它自动完成「暂存 → 提交 → 推送」，不等同于「全自动合并」**。看清边界再依赖它。

**脚本替你执行的（等价 git 命令）**

```powershell
git add -A -- frontend                                   # 默认只暂存前端代码目录
git commit -m "feat(users): 用户列表支持组合筛选"
git push -u origin feature/daily-20261110                # 推到当天的功能分支
```

外加两条保护：暂存区若出现 `frontend/` 以外的文件、或 `.env` / `node_modules` / `dist`，直接中止；没有任何改动时提示并退出，不产生空提交。

**参数**

| 命令 | 作用 |
| --- | --- |
| `.\scripts\daily.ps1 "feat(goods): …"` | 当天首次运行自动从 `origin/develop` 切出 `feature/daily-<日期>`，之后同一天追加提交 |
| `.\scripts\daily.ps1` | 不写说明，用默认 `chore(daily): <日期> 日常提交` |
| `.\scripts\daily.ps1 -Scope all "docs: …"` | 连 `backend/`、`研发流程/` 一起提交（默认不含） |
| `.\scripts\daily.ps1 -DryRun` | 只打印将执行的 git 命令与文件清单，不落地 |

**必须由人做的部分（脚本不做，也不能代替）**

| 环节 | 原因 |
| --- | --- |
| 写代码并**保存到磁盘** | 脚本只提交已保存的内容，未保存的编辑器缓冲不会被提交 |
| 开 PR 并点 **Squash and merge** | Git Flow 要求 `feature → develop` 走 PR（§1.3）；脚本只推分支，不建 PR |
| `main` / `develop` 的合并 | 两条长期分支受保护，只能通过 PR（§1.1） |
| 解决冲突、`git pull --rebase` | 推送被拒（远端有新提交）时需人工处理 |
| 只提交部分文件 | 脚本默认全量 `frontend/`；要挑文件就自己 `git add <file>` |
| 修正提交说明 | 未推送时 `git commit --amend`；已推送则再提一次修正，**不要** amend 已推提交 |

**定时快照（可选，不是「自动开发」）**

计划任务每天固定时间跑一次 `daily.ps1`，只适合当「兜底快照」：它会把当时磁盘上**未写完的代码**一并提交到当天分支（仍在 feature 分支，不会进 `develop`）。启用与停用命令：

```powershell
$repo = "D:\test\学习\项目_react\admin-dashboard"
$pwsh = (Get-Command pwsh).Source
$act  = New-ScheduledTaskAction -Execute $pwsh -Argument "-NoProfile -File `"$repo\scripts\daily.ps1`" -Message `"chore(daily): 自动快照`""
$trg  = New-ScheduledTaskTrigger -Daily -At "18:30"
Register-ScheduledTask -TaskName "admin-dashboard 每日提交" -Action $act -Trigger $trg -Description "每天 18:30 提交 frontend 改动并推送"
Unregister-ScheduledTask -TaskName "admin-dashboard 每日提交" -Confirm:$false   # 停用
```

**结论**：自动化到「提交 + 推送」为止；**合并仍然是人工的、只接受「一段活干完」的信号**。不要用它代替 §4 的 Review 清单与 §7 的自测清单。

## 2. Commit Message 规范（Conventional Commits）

格式：`<type>(<scope>): <subject>`

| type | 含义 |
| --- | --- |
| feat | 新功能 |
| fix | 修复缺陷 |
| docs | 文档 |
| style | 样式/格式（不改逻辑） |
| refactor | 重构（不改功能） |
| perf | 性能优化 |
| test | 测试（含 Apifox 场景脚本） |
| chore | 构建/依赖/杂项 |

示例：

```
feat(users): 用户列表支持 keyword/role_id/status 组合筛选
fix(auth): 修复 token 过期后未跳转登录页的问题
refactor(api): 统一 request 拦截器按 code 判断成败
test(apifox): 场景 test1 补充角色菜单读回断言
```

**要求**：一次提交只做一件事；subject ≤50 字；破坏性变更在 body 说明。

## 3. 代码规范

### 3.1 通用

- 前端 ESLint 用 Vite 模板自带配置（`eslint.config.js`）；提交前 `npm run build` 不报错。
- 命名：组件 `PascalCase`（`UserTable.jsx`）、变量/函数 `camelCase`、常量 `UPPER_SNAKE`；文件与目录风格统一。
- **禁止**在代码里硬编码账号/密码/密钥/后端地址；配置集中在 `.env` + `src/config`。
- 目录结构遵循 [`../开发文档.md` 第 8 章](../开发文档.md)。

### 3.2 前端

| 项 | 约定 |
| --- | --- |
| 构建 | Vite 8（`frontend/` 实际），端口 **5173**；**需自行补** `server.proxy['/api'] → http://localhost:3000`（脚手架默认没有 proxy） |
| 请求层 | 所有请求走 `src/api/*`；组件内**禁止**裸写 axios/URL |
| 成功判定 | **`code === 0`**；业务错误是 HTTP 200 + `code:1` |
| 401 处理 | 拦截器统一清 store → `window.location.replace('/login')` |
| 状态管理 | 全局只有 `useUserStore`（token/user/menus/permissions）；页面局部状态用 `useState` |
| 表单 | 受控 + 提交前校验；提交中 `loading` 且禁用，防重复点击 |
| 反馈 | 增删改 `message.success`，失败 `message.error`；删除前 `Modal.confirm` |
| 路由 | `routes.js` 声明静态路由元数据，`guard.jsx` 做登录守卫 + 权限过滤 |
| 权限 | 侧栏用 `menus` 建树，按钮用 `<Auth permission="user:create">` |
| 样式 | `styles/tokens.css`（与 02 文档同源）+ antd `ConfigProvider` token；不另起品牌色 |
| 图表 | `ChartBox` 统一封装：`ResizeObserver → resize()`、卸载 `dispose()` |

### 3.3 后端

- 路由只做参数解析与转发，业务在 controller，SQL 在 controller 内参数化执行。
- 响应统一走 `utils/response.js` 的 `success / fail / paged`，**不要自己 `res.json`**。
- `fail(res, message, httpStatus = 200, code = 1)`：业务错误默认 200，只有 401/404 用真实状态码。
- SQL 一律 `?` 占位，禁止字符串拼接。
- 控制器 `try/catch(err => next(err))`，交给 `errorHandler` 统一兜底。
- 新增接口必须同步更新：`研发流程/03` 契约、`研发流程/api-openapi.json`、`开发文档.md` 第 7 章。

## 9. 提交与发布纪律

- 合并前必须 CI 通过（构建 + 基本检查）。
- 不在 `main` / `develop` 直接提交；两条长期分支均受保护（§1.1）。
- 合并方式按 §1.3 矩阵执行：`feature` 用 Squash，`release/hotfix/回灌` 用 Merge commit。
- **发布必须回灌**：`release → main` 与 `hotfix → main` 之后，务必 `main → develop`，否则下个版本重复提交、反复冲突。
- 发布打 Tag（`v1.0.0`），**Tag 只打在 `main` 上**，与线上版本一致。
- **`npm run init-db` 会 DROP 重建数据库**：只在本地/测试库执行，生产环境禁止。
- 每次发布更新《上线记录》（见 05 文档）。
